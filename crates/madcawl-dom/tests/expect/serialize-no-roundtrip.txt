# Cases where parsing, serializing by the HTML fragment serialization
# algorithm (HTML 13.3) and parsing again does not give the same tree,
# because of the algorithm itself, one per line as
# <file>:<line of its #data or #description> <class>. A listed case that
# round trips, or an unlisted one that does not, fails the test.
#
# doctype-ids      a DOCTYPE is written as `<!DOCTYPE name>`: its public
#                  and system identifiers are not written, so they are
#                  lost, and with them the quirks mode they chose (which
#                  in quirks01.dat also moves a table out of a p)
# plaintext        nothing ends a plaintext element once it starts: its
#                  end tag, the end tags after it and any element the
#                  parser put inside it come back as its text
# script-escape    the script text ends inside `<!--<script`, the double
#                  escaped state, where `</script>` does not end the
#                  script, so the end tags written after it become
#                  script text
# leading-newline  the parser drops a newline right after `<pre>`,
#                  `<textarea>` or `<listing>`; the algorithm does not
#                  write an extra one (the note at the end of 13.3), so a
#                  text starting with a newline loses it
# carriage-return  a U+000D in text (from `&#x000D;`) is written as it
#                  is, and the parser turns it into U+000A
# nesting          a tree markup cannot express: an a inside an a, a
#                  nobr inside a nobr (foster parenting and the adoption
#                  agency), a p inside a p, a form inside a form; the
#                  reparse closes the outer element or ignores the inner
#                  start tag (the examples in 13.3)
